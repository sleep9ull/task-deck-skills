# 后台运行与恢复

## 执行载体

优先使用已有作业系统的提交、查询、暂停和恢复接口。没有时可用普通后台进程：Python `subprocess.Popen([...], start_new_session=True, stdin=DEVNULL, stdout=日志文件, stderr=STDOUT)` 适用于 POSIX 的会话脱离；Windows 使用等效的独立进程/作业机制。这不保证主机重启后存活；确需跨重启时选择可用的服务管理器或调度器，并保存任务身份。

所有命令通过参数数组传递，路径按所在主机解析。重定向所有标准流，避免 SSH 退出仍等待输出管道。记录任务 PID 与启动时间/命令指纹，停止前重新核验身份；只操作本任务拥有的进程或进程组。

执行主机与控制主机不同，则将业务循环放在执行主机上，控制端只提交任务、查询状态、拉取结果；避免每件工作跨 SSH 往返。凭据和浏览器会话留在授权主机，不随状态文件同步。

## 运行目录示例

```text
runs/<run-id>/
  plan.json              # 固定范围、批次和验收条件
  status.json            # 原子写入的页面状态，契约见 status-contract.md
  index.html             # 从状态生成的单文件监控页
  session.json           # 主机、进程/作业身份、启动与恢复命令
  events.jsonl           # 追加事件，页面只选取近期窗口
  worker.log
  batches/<batch-id>/
    input.jsonl          # 不可变输入或其稳定引用
    attempts.jsonl       # item key、attempt ID、结果、证据和时间
    results.jsonl
    checkpoint.json      # 本批提交状态与结果摘要/hash
    evidence/
```

按照实际任务缩减目录。每次运行产生的这些文件位于用户任务项目内，不在 skill 的安装目录中。

## 提交与恢复

1. 领取 item 前检查暂停/停止信号；以稳定 item key 去重。
2. 保存业务结果和证据，再提交完成记录；原子替换检查点，必要时 flush/fsync。
3. 从已提交记录推导批次计数，再原子替换 `status.json`，触发渲染。
4. 心跳独立于慢业务步骤更新，进程核验独立于心跳写入；状态携带各自观察时间。
5. 若外部写入已发生而本地记录尚未提交，恢复先对账或复用幂等键，不能仅靠“本地没结果”重复写入。

同一 run 只允许一个协调写入者；并发 worker 可把结果交给协调者，或使用明确的互斥提交协议。失败是结果而非无限重试指令。每次恢复跳过已提交条目；重新尝试失败项要按计划的重试预算或用户新指示执行，并保留前次证据。

终止信号停止派发后，让在途任务提交或记录中断。崩溃留下不完整尾行时，隔离并修复未提交尾部，保留已提交记录；不要重置整个批次。

远端完成文件先写内容，再发布完成标记/hash；本地同步先验证内容与标记一致，再合并导出。临时传输失败只影响镜像新鲜度，不应重启仍活跃的远端 worker。

## 验证与交接

上线真实全量前，验证最小批次、一次暂停恢复、一次失败分类，以及页面的新鲜度警示。涉及有副作用的任务，恢复演练在本地模拟或隔离测试范围进行；不为测试重复外部写入。

交接至少包含 HTML 绝对路径、run ID、真实执行主机/句柄、最后核验时间、当前计数、输出位置和暂停/恢复方式。仅在已部署了持续执行载体时说“后台继续”；需要未来自动唤醒或定时运行时使用环境支持的调度能力，不把普通聊天回复当调度器。
